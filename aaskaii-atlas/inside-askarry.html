Why not just ask a language model?

A large language model (LLM) is trained once, on a fixed body of text, and then it stops learning. When a user asks an LLM to intrepret a document (or set of documents), these documents are parsed and stored in short-term memory, known as context memory. After the current session is over, the context memory is cleared. The model has no long-term memory of what it read, and it cannot learn from the documents for future sessions.

LLMs have a limited (but rapidly increasing) context memory, which is measured in small chunks of text called tokens. Frontier LLMs can deal with about ~1 million tokens; locally-hosted LLMs have order-of-magnitude smaller contexts. When context memory is filled, the session has to drop data (i.e. forget stuff). The SKA corpus of AASKA, AASKA II chapters and a few technical documents comes to about 6 million tokens. That means that even frontier LLMs (at least as of writing) cannot hold the entire corpus in context memory.

Two other things happen when context memory gets filled. Firstly, it gets expensive: the more tokens used, the more the user pays. Secondly, the models 'attention' gets diluted and the model can start to hallucinate, filling gaps in its memory with general statistical associations learned during training (i.e. its parametric memory). Hallucinations may sound convincing so are hard to spot, and they are often incorrect nonsense.

Retrieval-augmented generation (RAG) changes the task instead of trying to fix the model's memory. The system first searches a fixed collection of real documents for the passages most likely to contain the answer. It then hands the model those passages and instructs it to answer using only what is in front of it. This resembles an open-book exam rather than a closed-book one. The model's job shrinks from recalling a fact to reading a handful of passages and summarizing what they say. Language models perform that second task far more reliably, because it does not depend on what survived in their training data.

ASKARRY is a RAG system built around the AASKAII science case and a smaller set of SKA engineering documents. The sections below describe how it turns a folder of PDFs into a system you can query. Each answer carries a citation, so you can verify it rather than simply trust it.

The pipeline, in outline

The pipeline runs in two separate phases. The first phase runs once, offline, whenever new papers are added. It parses PDFs, cuts them into small pieces, and indexes those pieces in two different ways. The second phase runs every time someone asks a question. It matches the question against both indexes, merges and re-orders the two result lists, and hands the best passages to a language model to write an answer. The diagram below shows both phases. Ingestion: turning PDFs into searchable pieces

A PDF is not searchable at a fine grain. You can search it for a word, but not for the passage that answers a specific question. Ingestion breaks each paper into small, self-contained pieces called chunks. Each chunk is short enough to search and reason over individually.

Askarry uses a library called Docling to parse each PDF into a structured document. Docling identifies headings, paragraphs, page numbers, and figure captions, rather than treating the PDF as one undifferentiated block of text. A component called HybridChunker then splits that structured document into pieces of roughly 480 tokens or fewer. A token is roughly three-quarters of a word, so 480 tokens is a little over one paragraph in most academic writing. This limit exists because the embedding and re-ranking models used later in the pipeline cap out at 512 tokens; chunks are kept comfortably under that ceiling. The chunker works from the document's actual structure rather than cutting text at a fixed character count. As a result, it rarely slices a sentence in half at an arbitrary point.

Every chunk is stored with metadata alongside its text. That metadata records which file and page the chunk came from, its position in the document, and the heading it falls under. It also records which of three document collections the chunk belongs to: the current AASKAII book, the older 2015 predecessor, or a separate set of SKA engineering specifications. This metadata lets the system show exactly where an answer came from, instead of merely asserting it.

Indexing: two different ways of remembering the text

Once the corpus is chunked, Askarry indexes it twice, using two different methods. Each method catches a different kind of question.

The first method builds a vector index. An embedding model, BAAI/bge-large-en-v1.5, reads each chunk and converts it into a long list of numbers called a vector. That vector represents the chunk's meaning. Chunks about similar topics end up as nearby points in this numerical space, even when they share few of the same words. This is what lets the system search by meaning rather than exact wording. A query about "detecting cold gas in galaxies" can still find a passage that only says "neutral hydrogen emission," because the embedding model has learned that the two phrases describe similar territory. Askarry stores these vectors in ChromaDB, a database built for fast nearest-neighbour lookups over large numbers of vectors.

The second method builds a keyword index, using an algorithm called BM25. BM25 scores how well a document matches a query based on which exact words the document contains, weighted by how rare and how frequent those words are. This is the same family of algorithm that underlies much of traditional web search. BM25 is strong exactly where embeddings are weak: it catches precise technical terms, acronyms, and instrument names, where exact wording matters more than general topic. Before running this search, Askarry expands the query with any acronym definitions it has learned. A question about "the CSP" also searches for "Central Signal Processor." This expansion measurably improves recall, because this corpus is written in acronym-heavy language.

Neither index alone is sufficient. Semantic search can miss a rare, precisely worded technical query. Keyword search can miss a well-phrased conceptual one. Askarry runs both searches for every query and combines the results; the next stage explains how.

Retrieval: finding the right passages

Askarry searches every question against both indexes independently. This produces two ranked lists of candidate chunks, typically the top 20 or so from each. The engineering problem is that the two lists' scores are not directly comparable. A cosine similarity from the vector index and a BM25 score sit on completely different numerical scales. Simply adding the two scores together would let whichever scale happens to run larger dominate the result, for no principled reason.

Askarry solves this with Reciprocal Rank Fusion (RRF). RRF ignores the raw scores entirely and works from rank position instead. Each chunk earns a fusion score of 1 / (60 + rank) from each list it appears in, where rank is its position (1st, 2nd, 3rd, and so on) in that list. Askarry adds the two contributions together, weighting the keyword-search contribution at roughly half the semantic contribution. That weighting is tuned for how acronym-dense this corpus is. The constant 60 dampens the score: without it, the difference between ranking 1st and ranking 2nd would swing the fused score far more than such a small difference in relevance actually warrants. A chunk that ranks respectably in both lists will usually outscore a chunk that ranks first in only one list. This is the reason to run two searches instead of one.

Askarry hands the fused list to a cross-encoder, a second relevance model that is slower but more accurate. The embedding model used for semantic search reads the query and each chunk separately and then compares the two representations. That approach is fast enough to run over the whole corpus, but it is comparatively coarse. A cross-encoder reads the query and a candidate chunk together, as one input, so it can judge their relevance to each other far more precisely. This precision costs more compute, so it only makes sense once the field has already narrowed from thousands of chunks down to a few dozen. This retrieve-broadly-then-rerank-precisely pattern is standard in modern search systems for that reason. Askarry also applies a modest, tunable penalty to chunks from the outdated 2015 predecessor book. Current AASKAII material wins relevance ties as a result, without excluding the older source outright when it is genuinely the better match.

Finally, Askarry expands each surviving chunk with its immediate neighbours in the source document. By default it joins the chunk before and the chunk after into one combined passage. Chunk boundaries are somewhat arbitrary, and a sentence explaining a result can fall right at the edge of one. This expansion step reduces the chance that the passage handed to the language model is missing context it needs.

Key terms

Embedding
a numerical representation of a piece of text that places similar meanings near each other in a high-dimensional space.
BM25
a statistical formula for ranking documents by exact keyword match, accounting for word rarity and document length.
Reciprocal Rank Fusion
a way of combining two ranked lists using each item's rank position rather than its raw score, so incomparable scoring scales don't distort the result.
Cross-encoder
a model that scores a query and a passage jointly, rather than comparing separately-computed representations — slower, but more accurate.

Generation: writing the answer

Retrieval only finds passages. Generation turns them into prose. Askarry assembles the retrieved passages into a numbered context block and hands that block to a language model along with a system prompt. The prompt functions as a set of exam instructions. It tells the model to answer only from the passages provided, to cite every factual claim with a bracketed number matching its source passage, to state plainly when the passages lack a good answer instead of guessing, and to write in plain declarative sentences without promotional language. If the strongest match scores below a confidence threshold, Askarry adds an extra instruction telling the model to treat the material with visible scepticism instead of forcing an answer.

The prompt also supports two audience settings. When set to write for a PhD astronomer, the model uses standard notation and technical vocabulary without defining it. When set to write for a general reader, the model defines acronyms and terms on first use and explains equations in words instead of leaving them unexplained.

Two front doors

Askarry offers two separate ways to ask it a question, and each uses a different model to write the final answer.

The first is a Gradio web app, the browser interface most people use directly. It runs the whole pipeline described above and then generates the answer with a small language model, Gemma, running locally through Ollama. No data leaves the machine it runs on. The trade-off is that a locally run model is less capable than a large frontier model.

The second is an MCP server, a small piece of software that exposes the retrieval pipeline as a set of callable tools to any MCP-capable assistant, such as Claude. In this mode, Askarry skips the local generation step entirely. Retrieval runs exactly as described above, and the assistant itself reads the returned passages and writes the answer, using its own larger reasoning capacity. Every document in this atlas was produced through this second path, by calling the retrieval tools directly rather than through the web app.

Askarry exposes six tools this way. Three mirror the pipeline already described. One searches the AASKAII passages. One lists the available papers. One retrieves every indexed chunk of a single named paper in order, for close reading of that one document rather than a search across all of them. A fourth and fifth tool repeat the search-and-list pair over a separate, smaller set of SKA engineering specifications. Askarry keeps these specifications apart from the science papers because they answer a different kind of question. The sixth tool is not a document search at all. It forwards a request directly to SKAO's live sensitivity-calculator web service and returns the freshly computed answer. It is the only tool in the set that consults a running system rather than an indexed text.

A worked example

Suppose someone asks: "What sensitivity would a deep HI intensity mapping survey need to detect the cosmological signal at z ≈ 1?" The steps below trace that question through the pipeline.

1

Askarry embeds the question and searches it against the vector index. This surfaces chunks discussing HI intensity mapping and cosmological sensitivity requirements, including chunks that never use the phrase "z ≈ 1" verbatim, because the embedding model recognises the surrounding concepts.

2

Askarry expands the same question with any acronyms it contains (HI becomes neutral atomic hydrogen) and searches it against the BM25 keyword index. This surfaces chunks that use the exact terms "intensity mapping" and specific redshift or sensitivity figures.

3

Reciprocal Rank Fusion merges the two ranked lists. A chunk ranked 2nd by meaning and 4th by keyword typically outranks a chunk ranked 1st by keyword alone but absent from the semantic list entirely.

4

The cross-encoder re-ranks the merged shortlist. It reads the full question against each candidate passage together and reorders the passages by how directly each one answers the question.

5

Askarry expands the top few passages with their neighbouring chunks. This keeps a sensitivity figure quoted in one chunk together with the survey parameters explained in the chunk just before it.

6

Askarry hands the passages to a language model, either Gemma locally or Claude via MCP, with instructions to answer only from them and cite every figure quoted. The answer comes back with bracketed citations pointing directly to the source papers.

What this design does, and doesn't, fix

This pipeline substantially reduces hallucination, because it grades the model on comprehension of a supplied text rather than on recall from memory. It does not eliminate the risk entirely. The model still writes the final prose itself, so a careless summary of an accurately retrieved passage is still possible. Retrieval quality is bounded by what was actually ingested. A cleverer search algorithm cannot rescue a question about a topic the corpus never discusses. A question phrased very differently from how the corpus discusses it can still be missed by both search methods at once, though hybrid search makes this considerably less likely than either method alone. The system is also only as current as its last ingestion run. It has no awareness of anything published after that point.
